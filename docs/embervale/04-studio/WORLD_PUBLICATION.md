# Publish and select fixed world versions

**Implemented:** 20 November 2026 · **Task:** STUDIO-026, bounded starter-world scope.

Studio can validate a saved map, publish it under a new name and launch that exact version in a fresh game process. Earlier versions remain available. Selecting an earlier version rolls back the map used by the next launch.

## Use Studio

1. Open your map in Studio. If you have unsaved changes, use **Save new draft** first.
2. Press **Versions…**. Choose a version library directory and enter a new name, for example `village-v1`.
3. Press **Validate draft**. This checks the saved bytes with the game's current placement, spawn, building and access rules.
4. Press **Publish version**. The saved draft and previous versions are preserved.
5. Select a version in **Published versions**. Studio verifies it before enabling **Play selected version**.
6. Close an existing playtest before starting another. To roll back, select an older version and play it.

Studio launches with `--no-save` in a private temporary working directory. The selected fresh/development profile controls new-player initialization. A dirty draft can browse and play previous versions, but must be saved before it can be validated or published. The default library is `world-versions` beside the opened draft; `--library-dir` selects another location. `--publisher` selects the built `EmbervaleWorldPublish` executable if it is not beside `EmbervaleWorldMove`.

Selecting a version does not change normal no-argument game startup. There is no global “current version” file, live reload or automatic player-progress rollback. Each game process owns its loaded snapshot.

## Command-line workflow

Build with `GAMEENGINE_BUILD_CONTENT_TOOLS=ON`. The publisher is SDL-free. Use the paths from your build; Windows executables have the `.exe` suffix. These examples use Bash/MSYS2 redirection:

```bash
build-client/EmbervaleWorldPublish --validate content/drafts/village.json > village-receipt.json
build-client/EmbervaleWorldPublish --publish content/drafts/village.json \
  --receipt village-receipt.json --library content/published --revision village-v1
build-client/EmbervaleWorldPublish --inspect content/published/village-v1/manifest.json
build-client/GameEngine --world-version content/published/village-v1/manifest.json --no-save --profile fresh
```

Validation and inspection are read-only, including no lock-file creation. Validation writes a receipt to stdout; publishing writes a manifest to stdout. The publisher returns `0` on success, `1` for validation/file/publication failures and `2` for invalid arguments. Diagnostics go to stderr. On Windows PowerShell, use `Set-Content -Encoding ascii` to capture the receipt; legacy PowerShell `>` can otherwise create unsupported UTF-16 JSON. Studio handles this automatically.

The checked-in [River Crossing version](../../../content/published/README.md) is ready for inspection and launch. Publishing another map does not select it automatically.

## Validation is bound to exact input

The receipt records both the SHA-256 of the original saved file and the SHA-256 of its canonical validated world. Even a whitespace-only source change requires validation again. Publishing independently validates the candidate, compares its receipt, then holds the existing cooperative source lock while rechecking the exact source hash and writing the version.

The `validator_revision` is a SHA-256 generated by CMake from the core implementation sources, source headers, build definition/template, platform and compiler ID/version. Input changes trigger regeneration. This identifies recorded validation inputs; it is not a binary signature, a complete compiler-flags fingerprint or proof of authorship. A receipt from a different revision must be regenerated before publication.

Current validation supports the existing 100×100 starter registry, world schemas 1–4, supported terrain, stable authored IDs, allocation reservations, actor/spawn authority, placement occupancy, buildings/doorways and required approaches/routes. Broader regions/exits and richer structured diagnostics remain separate work. Publication does not widen the schema or make invalid unfinished edits saveable.

## Package and metadata

Each named version has exactly two required files:

```text
content/published/village-v1/world.json
content/published/village-v1/manifest.json
```

| Field | Receipt | Manifest | Meaning |
|---|---|---|---|
| `receipt_version` | `1` | Absent | Receipt metadata schema |
| `manifest_version` | Absent | `1` | Manifest metadata schema |
| `revision` | Absent | Required | Name of the containing version directory |
| `world_file` | Absent | `world.json` | Fixed payload leaf; paths/traversal are rejected |
| `source_sha256` | Required | Required | Exact saved input bytes |
| `world_sha256` | Required | Required | Exact canonical published bytes |
| `world_schema_version` | `1`–`4` | `1`–`4` | Supported world format |
| `validator_profile` | `starter-runtime-v1` | Same | Required gameplay-validation contract |
| `validator_revision` | Required | Required | Recorded validation implementation fingerprint |

Unknown/duplicate fields, unsupported versions/types, malformed hashes and oversized metadata are rejected. Payloads are limited to 2 MiB and metadata to 4 KiB. Names contain 1–48 lowercase letters, digits or hyphens and start/end with a letter or digit; reserved Windows device names are rejected. Studio lists at most 256 library entries and never prunes old versions automatically.

The game checks the manifest/layout, payload hash, schema and canonical bytes, then validates the map with the current runtime rules before creating the Engine or reading a player save. Older validator revisions may load when the profile/schema are still supported and current validation succeeds. This preserves useful rollback across compatible engine changes without treating old evidence as current approval.

Published files/directories must be regular, non-symlink entries at the selected boundary. Application writers create fresh versions only. Checksums detect changed files; someone with filesystem write access can still alter a package and its hashes. Keep trusted copies in Git. Packages do not freeze the game binary, art/audio, RNG state or live world state.

## Interrupted publication and conflicts

The publisher reserves a new version directory exclusively, stages the complete canonical world and commits `manifest.json` last. A directory without its committed manifest is incomplete and cannot be selected as a published version.

| Interruption | Result on the tested local filesystem |
|---|---|
| Before name reservation | No new version |
| After reservation or after world write, before manifest | Incomplete directory; name remains reserved and is omitted from Studio's list |
| After complete manifest commit | Complete, inspectable version |
| Another publisher uses the same name | Refused; prior/partial files are preserved |

After an uncertain outcome, inspect the named manifest or refresh Studio. Use a fresh name if the old directory is incomplete. Unknown leftovers are never silently promoted, reused or recursively removed. Existing `.embervale.writer.lock` files are intentional OS-lock sidecars; do not unlink a live lock. Unknown legacy `.embervale.lock` directories are retained and source writes are refused. The [draft recovery guide](EDITOR_RECOVERY.md) remains the separate recovery path.

Linux process-kill tests cover reservation, world-written and committed-manifest boundaries, plus competing publishers. They establish process-interruption behavior for the exercised filesystem. Power-loss/physical-media durability, network filesystems and current Windows execution remain unverified.

## Player saves and remaining acceptance

`--world-version` keeps player progress temporary by default. Explicit `--save` opts into the existing persistence policy, but its primary, temporary and backup paths must be outside the whole selected version library and must not alias the selected map/manifest. Studio always uses `--no-save`. Player save format stays **13**; manifest/receipt formats are independently versioned at **1**.

An explicitly selected saved player uses the existing bounded imported-world position/recovery handling. Selecting an older map does not restore old items, quests or player state. General content/save migration, source overwrite, release packaging, asset manifests and online deployment remain separate scopes. See [save compatibility](../03-engine/SAVE_COMPATIBILITY.md).

Automated evidence includes distinct v1/v2/v1 fresh Worlds and real dummy-SDL game processes, unchanged private player fixtures, stale receipts, changed files, malformed/tampered packages and forced writer termination. A native Linux/Tk walkthrough validates, publishes, rejects a name collision and selects an older version. This environment's SDL build lacks desktop X11/Wayland drivers, so its native game-launch attempt reports failure; dummy-driver launches pass. Full native/Windows rendering and broader accessibility acceptance remain open.
