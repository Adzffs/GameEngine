# Architecture decision record template

## ADR identity

- Number and title:
- Status: proposed, accepted in implementation, superseded or rejected:
- Date, contributors and related planning IDs:
- Implementing PR/commit or superseding ADR:

## Context

What concrete problem requires a decision? What source, measurement, user constraint or compatibility obligation shapes it? Which assumptions remain unverified?

## Options considered

For each credible option, describe complexity, benefits, costs, compatibility, failure modes and reversibility. Do not list an obviously unsuitable alternative merely to justify the preferred choice.

## Decision

State the chosen rule, dependency boundary or representation precisely enough that implementation can be reviewed against it. State which details remain intentionally open.

## Consequences and validation

Describe affected data/saves/assets/API, migration, rollback, performance implications and tests or prototypes that support the choice. Link relevant specifications and evidence.

## Follow-up

List implementation work and triggers that would cause reconsideration. If superseded, preserve this rationale and link the replacement.
