# Getting started with GameEngine and Embervale

**Status:** Commands match the inspected CMake/CI configuration; they were not executed as a fresh build during this documentation review.  
**Baseline:** `e9d32932e8f9b27e96283313cca320058792a81f` · **Updated:** 18 November 2026

## 1. Choose what you want to run

| Goal | Configuration | SDL3 required? |
|---|---|---|
| Work on simulation and headless tests | Client OFF, graphics tests OFF | No |
| Play the development game and run all test groups | Client ON, graphics tests ON | Yes |
| Use Embervale Studio | Future roadmap deliverable | No Studio executable exists yet |

The project uses C++20 and CMake 3.20 or newer. It defines `GameEngineCore`, an optional `GameEngine` client and tests controlled by `BUILD_TESTING`. `GAMEENGINE_BUILD_CLIENT` defaults ON; the default for graphics tests follows that option. Set both flags explicitly when creating a headless build. [Source: CMakeLists.txt](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/CMakeLists.txt).

Begin in the repository root, the directory containing `CMakeLists.txt`. Keep build output outside source directories and use a separate build directory for each toolchain/configuration. Do not reuse a CMake cache generated by a different compiler.

## 2. Obtain the source and record your revision

For a new checkout, the repository is:

```bash
git clone https://github.com/Adzffs/GameEngine.git
cd GameEngine
git rev-parse HEAD
git status --short
```

If you already have a checkout, inspect its status before switching branches or updating it. Preserve your work; do not reset a working tree simply to make setup instructions match. Record the commit you actually build, since this document's evidence applies to its pinned baseline.

## 3. Linux headless development

The current Linux CI job uses a C++ compiler, CMake and Ninja. On an Ubuntu-like environment, its package installation is `build-essential`, `cmake` and `ninja-build`; install equivalent tools through your environment's normal package manager. [Source: CI workflow](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/.github/workflows/ci.yml).

From the repository root:

```bash
cmake -S . -B build-headless -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_TESTING=ON \
  -DGAMEENGINE_BUILD_CLIENT=OFF \
  -DGAMEENGINE_BUILD_GRAPHICS_TESTS=OFF
cmake --build build-headless --parallel
ctest --test-dir build-headless --output-on-failure -L headless
```

This configuration intentionally does not produce the SDL game window. To list discovered tests without running them, use `ctest --test-dir build-headless -N`. A successful configure or test listing is not a passing test run.

## 4. Windows client with MSYS2 UCRT64

The existing Windows CI uses the **UCRT64** MSYS2 environment and its matching compiler, CMake, Ninja and SDL3 packages. Use that environment consistently rather than mixing tools from unrelated MSYS2 subsystems or an old absolute compiler path. The package names in the inspected workflow are: [Source: CI workflow](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/.github/workflows/ci.yml).

```bash
pacman -S --needed mingw-w64-ucrt-x86_64-gcc \
  mingw-w64-ucrt-x86_64-cmake \
  mingw-w64-ucrt-x86_64-ninja \
  mingw-w64-ucrt-x86_64-sdl3
```

Then configure and build from the repository root:

```bash
cmake -S . -B build-client -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DBUILD_TESTING=ON \
  -DGAMEENGINE_BUILD_CLIENT=ON \
  -DGAMEENGINE_BUILD_GRAPHICS_TESTS=ON
cmake --build build-client --parallel
ctest --test-dir build-client --output-on-failure -L headless
SDL_VIDEODRIVER=dummy ctest --test-dir build-client --output-on-failure -L client
SDL_VIDEODRIVER=dummy ctest --test-dir build-client --output-on-failure -L graphics
```

These shell examples target MSYS2 Bash. The dummy video environment is for automated tests, not normal play. From the repository root, launch the built Windows game with:

```bash
./build-client/GameEngine.exe
```

If SDL3 cannot be found, verify the selected toolchain and the package installation before adding arbitrary include/library paths. CMake requests SDL3 through its config package. The inspected repository does not establish a separately tested Linux graphical-client or macOS onboarding procedure; add those after recording a real build on each platform.

## 5. Understand saves and development boosts

`main.cpp` selects `saves/development-player.save` relative to the process working directory. Running from the repository root and running from a build directory can therefore use different saves. There is no current command-line save-path option in `main`. The configuration type supports an optional path in code, but that is not a shipped CLI. [Sources: main.cpp](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/src/main.cpp), [EngineConfiguration.h](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/src/Core/EngineConfiguration.h).

Keep ordinary development saves separate from test fixtures. Before a save-related experiment, preserve a copy and record the launch directory. Do not delete your save as a routine troubleshooting step. Normal controlled shutdown is the documented save boundary; a forced termination is not guaranteed to preserve progress. [Source: DevelopmentPlayerPersistence.md](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/docs/DevelopmentPlayerPersistence.md).

The current `ENABLE_TEST_PLAYER` setting is true. New development-default players receive boosted Woodcutting, Mining and Smithing XP. A newly created development save is consequently not a genuine unboosted starter account. The roadmap includes a dedicated fresh-player test profile before measuring onboarding and upgrade pacing. [Sources: DevelopmentConfig.h](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/src/Core/DevelopmentConfig.h), [Player.cpp](https://github.com/Adzffs/GameEngine/blob/e9d32932e8f9b27e96283313cca320058792a81f/src/Player/Player.cpp).

## 6. VS Code and other editors

Use the portable CMake commands above as the source of truth. Configure your editor to use the actual local compiler and chosen build directory. If you create a local debug launch configuration, set its executable to that build's output and choose its working directory deliberately because saves are relative to it.

Machine-specific `.vscode` files containing paths such as `c:/GameEngine` are not portable onboarding. Keep personal settings local. Shared presets or editor configurations can be added later when they use workspace-relative paths, match supported toolchains and have been verified. Do not substitute a new untested configuration for a removed stale one merely to preserve the filename.

## 7. When something fails

Record the exact commit, command, tool versions, build directory and error output. Separate configure failures, compilation failures, test failures and runtime failures. A workflow failure with no usable steps does not establish that the game tests failed.
